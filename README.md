# sagents-translate

Локальный CLI для литературного перевода по главам: очистка исходника → извлечение контекста → черновик → сверка с оригиналом → редактура → итоговая сверка. Каждый этап сохраняется; повторный запуск продолжает незавершённую версию. Принятие перевода — отдельное действие пользователя.

Первый сценарий — китайский текст 木葉手記 → русский с главы 1. Имена, техники, канон и правила конкретной книги задаются в материалах проекта. В коде и шаблонах нет привязки к произведению или вселенной.

## Запуск

Нужен **Node.js 24.9+**. Зависимостей времени выполнения нет; TypeScript и типы Node нужны только для проверки разработки. MVP проверен на Linux с локальной файловой системой.

```sh
npm ci
npm run check
npm test

# Полностью локальный пример, без провайдера и оплаты.
# Каталог назначения должен быть новым.
node examples/offline-demo.ts ./books/demo
node src/cli.ts status ./books/demo
```

Пример использует два синтетических абзаца и подставной backend. Он создаёт принятую `v0001` и новую, ещё не принятую редакцию `v0002`. Это проверка работы инструмента, не оценка качества модели. Результаты находятся в `books/demo/chapters/0001/versions/`.

Для настоящей книги отдельно установите и настройте [sagents](https://github.com/jointsome0-lgtm/sagents). Его авторизация, ключи, подключения и ограничения остаются в sagents. Переводчик не читает его файлы credentials и не реализует вход. Если `sagents` уже авторизован у текущего пользователя, повторный вход для переводчика не нужен.

Подготовьте UTF-8 файлы `001.txt`, `002-title.md`, … в каталоге исходников; один файл — одна глава. Подкаталоги и симлинки не импортируются. В новых книгах по умолчанию выбраны роли:

| Этап | Модель по умолчанию |
| --- | --- |
| Очистка | `gpt-6-sol@low` |
| `extract`: имена, термины, вопросы и знания персонажей | `gpt-6-astra@max` |
| Черновик, сверка, редактура, итоговая сверка | `gpt-6-astra@low` |

Это изменяемая стартовая конфигурация, не результат сравнения литературного качества моделей.

```sh
node src/cli.ts init ./books/muye-shouji --source ./books/chapters --from zh --to ru
node src/cli.ts prepare ./books/muye-shouji --number 1
# Проверьте cleaned.txt, cleanup.json и extraction.json по путям из вывода.
# При необходимости согласуйте предложения и отредактируйте context/glossary.json.
node src/cli.ts chapter ./books/muye-shouji --number 1
node src/cli.ts status ./books/muye-shouji

# Сначала прочитайте translation.md и remaining-issues.json указанной версии.
node src/cli.ts accept ./books/muye-shouji --number 1 --version '<version>'

# Замечания храните вместе с книгой.
node src/cli.ts revise ./books/muye-shouji --number 1 --notes ./books/muye-shouji/feedback.md
node src/cli.ts accept ./books/muye-shouji --number 1 --version '<new-version>'
```

`<version>` и `<new-version>` замените на номера из вывода CLI: правка контекста между подготовкой и переводом создаёт следующую версию.

`init` **копирует** исходники в `book/sources/`. После импорта редактируйте эти копии: изменения внешнего каталога автоматически не подхватываются. Запуск `chapter` с теми же входными данными продолжает прежнюю версию, а после изменения исходника, выбранного контекста, правил или настроек модели создаёт следующую. Уже сохранённые версии остаются на месте.

Можно выполнить `npm link` из checkout и использовать `sagents-translate` вместо `node src/cli.ts`. Это запуск из связанного checkout, без сборки. Публикация npm-пакета с компилированным JavaScript в MVP не предусмотрена.

## Команды и настройки

| Команда | Действие |
| --- | --- |
| `init <book> --source <dir> --from zh --to ru` | Создать проект, скопировать главы и редактируемые шаблоны |
| `prepare <book> --number 1` | Очистить исходник, извлечь предложения контекста и остановиться для просмотра |
| `chapter <book> --number 1 [--model <id>]` | Подготовить или переиспользовать подготовку, затем выполнить цикл перевода |
| `revise <book> --number 1 --notes <file>` | Новая версия с учётом замечаний; подготовка и цикл перевода |
| `accept <book> --number 1 --version v0002` | Явно принять завершённую актуальную версию |
| `status <book>` | JSON со всеми версиями, прогрессом, принятым текстом, устареванием материалов и usage |

`revise` берёт принятую версию, а если её нет — последнюю завершённую версию `chapter`. `--base v0002` выбирает другую завершённую основу. Без `--model` редакция использует модель основы. Повторение тех же замечаний с той же основой возобновляет ту же редакцию. После принятия новой основы те же замечания означают уже новую редакцию. Если исходник или результат очистки изменился относительно основы, сначала выполните `chapter`.

`prepare`, `chapter` и `revise` принимают `--model` (четыре этапа перевода), `--clean-model`, `--extract-model`, `--timeout <1..3600 секунд>` и `--api-max-tokens <n>`. Остальные настройки находятся в `book.json`:

```json
{
  "backend": { "command": "sagents", "args": [], "structuredOutput": true },
  "settings": {
    "model": "gpt-6-astra@low",
    "cleanModel": "gpt-6-sol@low",
    "extractModel": "gpt-6-astra@max",
    "timeoutSeconds": 600,
    "apiMaxTokens": null,
    "retries": 0,
    "maxParts": 8
  }
}
```

Это фрагмент файла, не замена всего `book.json`. Все три роли можно заменить доступными в sagents идентификаторами. В старых книгах без `cleanModel` и `extractModel` обе роли используют основную модель. `model: null` по-прежнему требует `--model`. `retries` — 0–2 дополнительных повтора неудачного этапа за один запуск CLI; по умолчанию повторов нет. Невалидный ответ никогда не становится готовым этапом. `budget_exceeded` останавливает работу сразу, даже если повторы разрешены. После устранения причины повторите ту же команду. Сохранённые этапы не вызываются заново.

Адаптер запускает исполняемый файл с массивом аргументов, **без shell**, и передаёт весь JSON через stdin. `backend.args` — только постоянные аргументы запуска, например абсолютный путь к локальному CLI при `command: "node"`. Не размещайте там ключи, credentials или тексты книги. При `structuredOutput: false` JSON Schema остаётся в инструкциях, но поле `schema` не отправляется в sagents; локальная проверка ответа сохраняется. Это ручная настройка для сервера без поддержки strict JSON Schema.

Для `api:<id>` поддерживается `--api-max-tokens`, который устанавливает `SAGENTS_API_MAX_TOKENS` только дочернему процессу. Если его нет и `settings.apiMaxTokens` равен `null`, используется окружение sagents. **2048 — изменяемый дефолт только API-подключения sagents 0.4.2**, а не общий предел переводчика. Значение применяется только к ролям с `api:`; остальные роли его не получают. Если ни одна роль не использует `api:`, параметр отклоняется. Усилие рассуждения передаётся в идентификаторе модели ровно по [контракту sagents](docs/backend.md).

Глава сначала переводится целиком. Только фактический `context_limit`, `output_limit` или превышение документированного размера запроса sagents запускает разбиение: сначала между абзацами, затем между предложениями. Затронутая часть проходит свой цикл заново; старые этапы остаются в истории. Очистка, `extract` и перевод имеют независимые деревья разбиения: максимум `maxParts` частей в каждом (1–64, по умолчанию 8), после чего инструмент останавливается. Лимит перевода не заставляет повторять очистку. Если ограничение вызвано большим общим контекстом или длинным неделимым предложением, нужно уменьшить контекст или изменить поддерживаемые настройки backend. Выдуманных оценок токенизации и автоматического переключения модели нет.

## Очистка и подготовка

`prepare` выполняет только `clean` и `extract`, сохраняет состояние `prepared` и возвращает пути к результатам. `chapter` с теми же настройками продолжает эту версию без повторной подготовки. Можно сразу запустить `chapter`, если отдельный просмотр не нужен. `accept` принимает только полный перевод, не подготовку.

Исходник в `sources/` остаётся неизменным. Модель очистки возвращает точные цитаты для удаления и их порядковые вхождения; приложение проверяет наличие цитат и отсутствие пересечений, затем удаляет только эти фрагменты. Замена или переписывание текста через этот этап невозможны. `cleaned.txt` — очищенный источник, `cleanup.json` — удаления с причинами и сомнительные фрагменты. Сомнительные места сохраняются; противоречащий этому ответ отклоняется. Границы абзацев и переводы строк нормализуются, традиционные/упрощённые иероглифы не конвертируются. Очиститель всё ещё может ошибочно назвать часть сюжета рекламой: проверяйте отчёт перед переводом.

`extract` получает очищенный источник и подходящие принятые записи. В `extraction.json` сохраняются кандидаты глоссария, вопросы, факты, знания, убеждения и трактовки с цитатами. Исходные термины и цитаты проверяются по тексту. Предложения доступны следующим этапам отдельно, с `accepted: false`, и не имеют приоритета над принятым контекстом.

Согласование в MVP — ручное: просмотрите `extraction.json`, перенесите одобренные записи в `context/glossary.json`/`notes.json`, задайте период доступности и обновите их `version`. Формат принятой записи отличается от предложения; пример ниже по ссылке. Затем запустите `chapter`. Изменение контекста создаст новую версию и повторит `extract` с принятыми решениями; неизменная очистка будет переиспользована. Правка feedback или модели перевода не требует повторных вызовов подготовки. Переиспользование отмечается в `reusedPreparation`, usage прежних вызовов учитывается только в исходной версии.

## Контекст и редакционная история

В `context/glossary.json` хранятся **принятые** написания имён и терминов. В `context/notes.json` — стиль, обращения, состояние сюжета, знания и предположения персонажей, переводческие трактовки, вопросы, возможные ошибки оригинала и замечания пользователя. Формат и примеры: [формат книги](docs/book-format.md).

У каждой записи есть `fromChapter` и `toChapter`: сведения из будущих глав отсекаются до составления запроса. Глоссарий выбирается по исходному термину/алиасам; заметки — по `match`, пустой список означает общую заметку. Это прозрачный поиск подстрок, без embeddings. Правильную временную разметку задаёт пользователь. Знание, полученное в конце главы N, обычно доступно лишь с N+1; внутри одной главы временной разметки пока нет.

Промпты находятся в `prompts/*.md`, их версия — в `prompts/manifest.json`. Они копируются в книгу при `init`; существующие файлы не меняются автоматически. Для старых книг без `clean.md`/`extract.md` используются встроенные шаблоны этих двух этапов. Чтобы редактировать их локально, скопируйте соответствующие файлы из `templates/prompts/` в `book/prompts/`. Хеш учитывает и текст файлов, поэтому правка без повышения номера версии тоже создаст новый результат.

`proposals.json` содержит предложения модели об изменении глоссария и заметок с указанием этапа и части. Ни завершение цикла, ни `accept` не переносят их в принятый контекст. Пользователь проверяет их и вручную переносит нужное в `context/`, выставляя главу доступности. `remaining-issues.json` содержит замечания итоговой сверки; версия может быть завершена с такими замечаниями. Решение о принятии остаётся явным.

## Надёжность и границы MVP

Все исходники, снимки контекста, результаты этапов, попытки и редакции находятся в проекте книги. `books/` исключён из Git; каждый созданный проект также получает собственный `.gitignore`. Диагностика содержит коды ошибок и номера этапов; stderr backend не печатается и не сохраняется. Тексты запросов не записываются в диагностические логи. Снимки материалов в `run.json` нужны для воспроизводимости и являются данными книги.

Запись использует временный файл, `fsync`, атомарный `rename` и блокировку проекта через встроенный `node:sqlite`. После аварии ОС освобождает блокировку; удалять `.write-lock.sqlite` нельзя. Один писатель на книгу; `status` читает уже зафиксированные снимки. Контрольная сумма не позволяет незаметно продолжить повреждённый checkpoint. На Node 24.9 предупреждение об экспериментальном SQLite ожидаемо. Каталоги NFS/облачной синхронизации и Windows не проверены.

`Ctrl+C`/`SIGTERM` прекращают дальнейшие этапы, но дают текущему `sagents ask` закончиться: его обновление credentials нельзя безопасно прервать через существующий CLI. Внешний watchdog ждёт timeout sagents плюс 125 секунд на обновление авторизации; затем завершает зависший процесс. `SIGKILL` сохраняет уже завершённые этапы, но ответ, ещё не записанный на диск, может потеряться. При возобновлении такой вызов выполняется повторно: ровно однократная оплата не гарантируется.

Usage сохраняется только в сообщённых полях, в том числе при структурно неправильном тексте модели. `knownTotal` — сумма известных значений, `unknownCalls` — попытки без соответствующего счётчика; при отсутствии данных сумма равна `null`. Включённые в input/output кешированные и reasoning токены не прибавляются к ним повторно. Стоимость не оценивается. Коды выхода: `0` — успех, `1` — ошибка, `3` — исчерпан бюджет, `4` — конфликт записи, `130` — отмена.

В репозитории по-прежнему шесть сценарных проверок через CLI: очистка/подготовка, сохранность принятого текста и смена исходника; возобновление; плохие ответы; бюджет; конфликт/аварийное завершение; разбиение по реальному ограничению. Проверяются также фильтрация поздних сведений и отсутствие выдуманного usage. Правила минимального тестового набора закреплены в [AGENTS.md](AGENTS.md). **Реальных модельных вызовов при разработке MVP не было**; литературное качество и поведение конкретного провайдера ещё требуют проверки пользователем.

Проверка схемы и наличия всех абзацев не доказывает смысловую полноту перевода. После разбиения сверки выполняются по частям; отдельной общей сверки стыков пока нет. Сверки выполняются с очищенным источником; они не проверяют, было ли удалённое рекламой. Модель может ошибаться в очистке, извлечении контекста, переводе и критике. UI, загрузчики сайтов, автоматический перевод всей книги, согласование блока глав, экспорт в EPUB/DOCX, автоматическое принятие контекста и автоматическая миграция схем остаются за пределами MVP.
