# Backend: sagents ask

Контракт проверен 2026-10-24 по upstream **sagents 0.4.2**, commit `4fe05be0369e8a8d3d954a97f137a219e731f7cf`:

- [`docs/ask.md`](https://github.com/jointsome0-lgtm/sagents/blob/4fe05be0369e8a8d3d954a97f137a219e731f7cf/docs/ask.md), blob `f0a2068e84ed542cc1d970e4eebe21c80e1617dd`.
- [`src/model.ts`](https://github.com/jointsome0-lgtm/sagents/blob/4fe05be0369e8a8d3d954a97f137a219e731f7cf/src/model.ts), blob `f7a62bcec9dd706267f8da6ceae0425a7507f587`.
- [`docs/connection.md`](https://github.com/jointsome0-lgtm/sagents/blob/4fe05be0369e8a8d3d954a97f137a219e731f7cf/docs/connection.md) и [`src/cli.ts`](https://github.com/jointsome0-lgtm/sagents/blob/4fe05be0369e8a8d3d954a97f137a219e731f7cf/src/cli.ts) для настроек подключения, timeout и кодов выхода.

Адаптер в `src/backend.ts` не импортирует sagents, не читает его credentials, не выполняет login. Интерфейс:

```ts
interface Backend {
  readonly identity: Record<string, unknown>;
  respond(request: Request, signal?: AbortSignal, monitor?: Monitor): Promise<Reply>;
}
```

`runChapter` принимает фабрику backend третьим аргументом и создаёт адаптер для каждой из трёх ролей: очистка, извлечение контекста и перевод. Для другой реализации достаточно заменить фабрику, оставив этапы и файловый формат. `identity` должна описывать влияющие на результат настройки без секретов; она входит в fingerprint. Настройка произвольной команды в `book.json` всё ещё ожидает протокол `sagents ask`, а не произвольный LLM CLI.

Процесс запускается как `spawn(command, [...args, "ask", "--timeout", seconds], {shell: false})`. Один JSON через stdin, один JSON через stdout. В запросе используются только `model`, `system`, `messages` с ролями user/assistant и необязательный `schema`. Текст запроса не попадает в аргументы процесса. `cache` допустим в upstream, но MVP его не задаёт.

`api:<id>` выбирает API-подключение. Остальные идентификаторы, в том числе `<id>@low`, `<id>@high`, передаются без преобразований; sagents поддерживает `minimal`, `low`, `medium`, `high`, `xhigh`, `max`. Суффикс усилия для `api:` не поддерживается upstream; используйте собственные поля сервера через окружение sagents. Настройка API `max_tokens` идёт через `SAGENTS_API_MAX_TOKENS`, а не поле запроса `ask`.

Адаптер фиксирует идентификатор модели, timeout, использование schema, путь/хеш исполняемого entrypoint и аргументы, эффективный API output limit, stream/cache-field. Для `SAGENTS_API_URL` и `SAGENTS_API_EXTRA` сохраняются только SHA-256, сами значения остаются в окружении. `SAGENTS_API_KEY` и прочие credentials не входят ни в снимок, ни в fingerprint. Изменения ключа не создают новую версию. Внутренние файлы установленного sagents за его entrypoint не хешируются; при обновлении backend учитывайте это явно. `adapter: sagents-ask/0.4.2` означает поддерживаемый контракт, не результат автоматической проверки установленной версии.

`done` принимается только при нулевом коде выхода, непустом `text`, валидном JSON-конверте и допустимых usage. Затем отдельно проверяется JSON внутри `text`: типы, поля, абзацы и порядок. `failed` принимается и при ненулевом коде выхода, как у настоящего sagents. Неизвестные коды, несколько JSON-ответов, не-UTF-8 и оборванный вывод отвергаются; полученный stdout остаётся в локальной сессии для разбора. Нормализованная ошибка содержит известный код и безопасные поля диагностики; исходный stdout сохраняется отдельно. Сам sagents 0.4.2 не выводит текст ошибки провайдера. Нормализованный `endpoint` успешного ответа сохраняется, если он присутствует.

`usage` может отсутствовать, быть `null` или содержать известные поля: `inputTokens`, `cachedInputTokens`, `writtenInputTokens`, `outputTokens`, `reasoningTokens`. Сохраняются только реальные неотрицательные целые значения либо `null`; пропуски не превращаются в нули. На невалидном/оборванном конверте надёжного usage нет. Если backend не вернул статистику неудачного вызова, она неизвестна.

Размер JSON-запроса проверяется по документированному лимиту **16 000 000 байт**; его превышение становится локальным `request_limit` и разрешает разбиение главы. Вывод процесса также ограничен 16 000 000 байтами как защита от неограниченного потока. Это ограничения транспорта, не токенов модели. В upstream у ChatGPT-подключения также есть защита от ответа длиннее 100 000 символов: её `output_limit` обрабатывается так же, как реальный лимит генерации. Автоматический подбор tokenizer/context window по имени модели не выполняется.

Отмена между запросами немедленна. Во время запроса backend ждёт его завершения, поскольку у `ask` нет канала кооперативной отмены и обновление токенов может занять до 120 секунд сверх его timeout. Завершённый ответ сохраняется; следующий этап не запускается. Переводчик оставляет sagents время закончить свою операцию.

`test/fixtures/fake-sagents.ts` — отдельный процесс с тем же stdin/stdout-контрактом. Он даёт воспроизводимые отказы и синтетические переводы без сети. Интеграционные проверки используют реальный subprocess-адаптер; платные подключения не вызываются.

`monitor` — необязательные callbacks `progress(diagnostics)` и `stdout(text)`. Адаптер сообщает начало процесса, heartbeat раз в 30 секунд и появление stdout. Он сохраняет только структурированные коды/параметры ошибок, HTTP-статус, время/размер вывода и статус завершения; текст stderr не передаётся. `runChapter` записывает полный исходящий запрос, stdout и ответ в JSONL внутри проекта книги. HTTP-заголовки с токенами через этот интерфейс не проходят.

Фаза `connect/stream` принимается, только если она есть в ответе backend. В sagents 0.4.2 библиотека знает её, но `ask` не включает её в JSON: переводчик не выдумывает пропущенное значение. Наличие целого JSON в stdout до завершения процесса видно по `backendStatus`; даже такой ответ не завершает этап до проверки кода выхода и структуры.

Сессия переводчика охватывает границу процесса `sagents ask`, а не внутренний HTTP/SSE-поток. `ask` буферизует ответ и печатает его целиком в конце; собственных журналов запросов он не ведёт и сессий Codex не создаёт. Поэтому `firstStdoutMs` — время до первого вывода CLI, а не до первого токена модели. Из этих событий нельзя отдельно измерить ожидание сервера, получение первого SSE-события и генерацию; для этого backend должен передавать дополнительные события.
